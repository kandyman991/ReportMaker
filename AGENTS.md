# ReportMaker engineering rules

Applies to humans, coding assistants and all PRs.

1. Treat ARCHITECTURE.md as a requirement contract. Never silently change a locked requirement; propose and review an ADR first.
2. Windows x64 is mandatory; Linux is optional. Do not claim Windows validation from Linux/headless tests.
3. Report projects are structured, editable data, separate from DOCX/PDF output and layout styles.
4. Reports have ordered intervention modules and a dedicated final conclusions section. Each module contains arbitrary ordered typed blocks (text, photo, table, nested module), not fixed Title/Description/Gallery forms. Keep photos with parent modules during moves.
4a. The editor module tree and generated summary/table of contents MUST be derived from the same ordered hierarchy. No separate summary data model. Report types are multi-select, not single-select. See docs/REPORT_COMPOSITION_CONTRACT.md and ADR-0006.
5. Languages are data, not hardcoded enums. Store original text and per-language translations separately; stale translations must be identifiable. UI locale is independent.
6. Customer -> site -> machine data is reusable, but a report MAY use manually typed customer/site/machine data with no master record. Capture report-level snapshots so old reports do not silently change when customer records change.
7. ChatGPT integration means a user-controlled browser view ONLY. No OpenAI API, bot/agent, injected scripts, scraping, message interception, account automation, password capture, bypass of login challenges or attempts to export cookies. Never assume embedded login succeeds. Externally open chatgpt.com if it fails.
8. Browser data is local to the user's profile; never include it in a project export, log, test fixture or Git repository. Clipboard transfer must be explicitly initiated by the user and treated as untrusted plain text.
9. Do not upload customer reports or machine photographs to a public repository. Tests must use synthetic information.
10. Significant changes require tests (including architecture invariants); link any architectural deviation to an ADR. Never merge PRs without explicit user authorization.
11. GitHub-backed continuity is mandatory: before work read CHAT_HANDOFF.md, docs/CHECKPOINTS.md, handoff/state.json (when available) and inspect live GitHub PRs/CI. At handoffs and milestone boundaries update curated checkpoints, with exact SHA, PR, verified tests, blockers and next action. Mechanical state.json is not architecture truth.
12. Publish Windows installers to rolling GitHub prereleases, not Actions artifacts. CI stays GitHub-hosted. Never upload customer CAD, reports, production screenshots or browser session data to GitHub, CI, AI or release assets.

PR checklist:
- Is the handoff/checkpoint current with the exact branch head, tests, and next action? Is the autogenerated snapshot treated only as mechanical metadata?
- Which requirements/ADR does this change implement?
- Have data model, editor UI and exporter boundaries stayed separate?
- Can modules be reordered/nested without losing photos and translations? Is the generated summary derived from that exact tree, rather than separately maintained?
- Can multiple intervention types coexist, and can a manual customer report be saved without a database master?
- Do languages remain open-ended?
- Are original report facts and user-approved text preserved?
- Does any new web capability violate browser-only/no-API restrictions?
- Was native Windows behavior actually tested, or is it explicitly pending?
- Are sensitive data and credentials absent from the diff?
