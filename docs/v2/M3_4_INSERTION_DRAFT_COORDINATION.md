# V2 M3.4 — Contextual block insertion and cross-editor draft coordination

**Date:** 2026-10-29. **Baseline:** `main` `b676bffdba9e7aa5f69753562cde514ea09da1ff`, after reviewed/merged PR #79 and continuity refresh. **Branch:** `feature/v2-m3-4-insertion-cross-tab`. **Architecture:** `docs/v2/ARCHITECTURE.md`, `docs/v2/BRANCH_EDITOR_REQUIREMENTS.md` BE-L04/L05, BE-E02/E05, BE-I01/I03/I04.

## Delivered scope

1. The Branch Editor's contextual insertion menu now covers **paragraph, heading, table, page break, and an existing project-owned photo**, either inside a module or after a content leaf. Inside a module also offers **submodule**. Existing top-level module insertion stays in the toolbar. Mixed insertion locations are computed from the read-only canonical `project_branch` projection and forwarded through the existing `CommandGateway`; there is no second list or drag-owned report model. Both toolbar and contextual entries include page breaks and existing photos. No extra or visible scrollbars are added.
2. `add_page_break` and `add_photo` are validated typed commands. Inserting a photo requires a safe logical asset ID already stored in the active `ReportSession.assets`. The user chooses an explicit existing asset, with the human-readable Gallery name where available. A project without owned photos gives feedback rather than inserting a dangling image. This step **does not import** outside files, decode browser content or fabricate media. Existing V1/M4/M4.5 media validation and bytes stay canonical and untouched. Photo placement and page-break rows render descriptive text; **photo thumbnails, caption editing, drag/paste imports and per-placement visual tools remain M4**.
3. Each typed insertion is one atomic `ProjectEditor` transaction, with stable new ID, canonical mixed order, Undo/Redo, .rmproj v4 persistence, existing languages/conclusion rules and unchanged export consumption. A context-menu action carries its original generation/revision through modal photo choice and rejects stale intents. Pending drafts reject structural changes.
4. The single `DraftCoordinator` now tags pending text/rich/table drafts with a **nonpersistent editor owner**. A future page Editor tab obtains an `EditorDraftPort` from the existing coordinator, not a second copy of the report. Same-field conflicts fail immediately; different fields can remain staged in parallel. Editor-owned draft Apply/Revert requires the original owner. A staged commit is still one guarded gateway transaction and does not clear another field's draft. Save/Open/New, Undo/Redo and other structural commands fail closed while *any* editor has unapplied drafts. All views share one source generation, revision, validation, translation provenance and persistence path.
5. Branch widgets show external draft values read-only with a notice rather than silently overwriting a page/editor edit. Stale text previews now have the same read-only/revertible recovery strategy introduced for stale table drafts in M3.3. Pending data stays copyable after a simulated concurrent source change, and Apply fails closed until explicitly resolved.

Tab integration, rendered photo editing and import remain M4/M6. Physical installed Windows 100/125/150% DPI, long reports, keyboard/menu/assistive technology and actual Word/PDF export remain M7 acceptance.
