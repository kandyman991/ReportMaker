## 2. Attestation vs. Authenticode signature

On the **isolated V2 non-release** workflow, an additional optional `workflow_dispatch` input `attest_nonrelease_metadata` defaults **false**. When and only when explicitly set true on the trusted `main` of this repository, and only after successful locked audit and hosted Windows install/uninstall, a distinct Ubuntu job downloads its **own run's metadata artifact**, validates source, config and runtime fields, and invokes `actions/attest` at reviewed full commit SHA using narrow `id-token: write`, `attestations: write`, `artifact-metadata: write` permissions. Untrusted PR and Windows build jobs still have no OIDC/signing permissions. This **attests the JSON provenance and CycloneDX SBOM files only**; it does not upload, publish, sign, or attest an installer binary. No attestation has yet been claimed/generated by this PR: it cannot execute the trusted-main-only job before merge and requires an explicit, separate opt-in after merge.

For future acceptance verify in a trusted environment:

```sh
gh attestation verify windows-v2-provenance.json --repo kandyman991/ReportMaker
gh attestation verify windows-v2-sbom.cdx.json --repo kandyman991/ReportMaker
```

Verify the **downloaded bytes** and expected provenance identity/digest, not merely that some attestation exists. The JSON is a claim about the Windows installer digest, not a direct signed installer assertion. Do not advertise this as a signed distributable.

**Authenticode remains BLOCKED:** no trusted release-signing identity/certificate, secure private-key custody, trusted timestamp server configuration, signer review, or verified Windows `signtool verify /pa /all <setup.exe>` evidence is present. Never generate a self-signed certificate and call it trusted, embed keys in GitHub Actions, or sign with an unreviewed certificate. A later *separate* owner-approved release PR must define protected environments/approvals, keyless/protected signing architecture, installer signature verification, independent download/digest checks, rollback and incident revocation procedure.

GitHub prerequisites/limitations: <https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations>. This public repository is eligible for GitHub attestations, but availability is not proof that this job has executed successfully.

## 3. Qt WebEngine/Chromium security gate

- Observed Windows V2 packaging: Qt/PySide6 **6.12.0**, Qt WebEngine **6.140.0**, Chromium engine **140.0.7339.225**, reported Qt security patch level **152.0.7977.83**. Versions are captured in the Windows provenance artifact.
- Qt separated WebEngine releases from core Qt starting at Qt 6.12: <https://www.qt.io/blog/qt-webengine-will-release-separate>. **Do not infer** from raw Chromium version alone that a particular Chromium CVE is present or fixed; assess Qt patch backports and API exposure.
- The October 27/29 Chrome stable 156 advisories list critical CVEs, including **CVE-2026-118306, CVE-2026-118331, CVE-2026-118348, CVE-2026-118344, CVE-2026-76024**. These are **triage candidates, not confirmed exploitable in this Qt binary**. Original advisories: <https://chromereleases.googleblog.com/2026/10/> and <https://chromereleases.googleblog.com/2026/10/stable-channel-update-for-desktop_0562499947.html>.
- `security/webengine_release_review.json` tracks each candidate as `untriaged`. `python scripts/check_webengine_release_risk.py --strict --provenance <actual-json>` **must fail** until independent Qt-vendor fix/non-applicability evidence is recorded for every critical CVE and the running binary matches the reviewed Qt version. The scheduled Qt watcher additionally reports the hold, **advisory-only** (it never publishes or breaks ordinary PR application CI).
- On a vendor release candidate, upgrade the complete matched PySide6 / QtWebEngine Windows lock, rerun offline native/HTML smokes, hash-matching repeat builds and HTML navigation security tests, and reassess advisories.
